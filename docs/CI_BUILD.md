# Сборка релиза через GitHub Actions — пошагово

Этот документ — для варианта «ничего не устанавливаю на компьютер, собираю в GitHub».
Итог: в разделе **Actions → Artifacts** лежит **подписанный `app-release.apk`** для RuStore,
а в логе прогона видно, что внутри APK настоящие рекламные ID и нет лишних разрешений.

Чем CI-путь отличается от локального:

| | Локально (Android Studio) | Через GitHub Actions |
|---|---|---|
| Что нужно установить | Android Studio + SDK (десятки ГБ) | ничего |
| Где ключ подписи | файл на компьютере | файл в секретах репозитория (`KEYSTORE_BASE64`) |
| Два файла воркфлоу | не нужны | нужно один раз вставить руками в веб-интерфейсе |
| Проверка на телефоне | `adb` из Android Studio | `adb` из standalone platform-tools или установка «с телефона» |
| Время сборки | 2–5 минут | 4–10 минут (первый прогон дольше) |

> Если ключа и секретов ещё нет — начинайте с шага A. Если всё уже настроено,
> переходите сразу к разделу «Короткий путь».

---

## Короткий путь (всё уже настроено)

1. GitHub → ваш репозиторий → вкладка **Actions** → слева **Android CI** →
   справа **Run workflow** → Branch: **main** → при необходимости вписать `version_code` →
   зелёная кнопка **Run workflow**.
2. Дождаться зелёной галочки (4–10 минут).
3. Внизу страницы прогона → блок **Artifacts** → **release-apk** → скачать →
   внутри `app-release.apk` (это и есть файл для RuStore).

Всё остальное ниже — про первый раз и про разбор поломок.

---

## Шаг A. Ключ подписи приложения

Ключ создаётся **один раз**, подписывает все будущие версии и никогда не меняется.
Потеря ключа = невозможность выпускать обновления.

### Вариант A1 (обычный): если на компьютере есть Java

Java есть, если установлена Android Studio, или отдельный JDK, или вы можете поставить
**Temurin 17** с <https://adoptium.net> (маленький установщик, ставить Android Studio не нужно).

**Windows (cmd):**

```cmd
cd C:\путь\к\проекту
set "JAVA_HOME=%ProgramFiles%\Android\Android Studio\jbr"
"%JAVA_HOME%\bin\keytool" -genkeypair -v -keystore app-signing.keystore -alias sign -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
"%JAVA_HOME%\bin\keytool" -list -v -keystore app-signing.keystore -alias sign
```

Если Android Studio нет, вместо первой строки подставьте путь к своему JDK, например
`set "JAVA_HOME=%ProgramFiles%\Eclipse Adoptium\jdk-17.0.13.11-hotspot"` (точное имя папки
посмотрите в `C:\Program Files\Eclipse Adoptium`).

**macOS / Linux:**

```bash
cd ~/путь/к/проекту
keytool -genkeypair -v -keystore app-signing.keystore -alias sign -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
keytool -list -v -keystore app-signing.keystore -alias sign
```

**Что вводить в вопросы keytool:** пароль (придумайте и запишите — он нужен в секретах),
повтор пароля, затем данные сертификата. Их видит пользователь в окне «Подпись приложения»
на телефоне, поэтому пишите осмысленно:

| Вопрос | Пример ответа |
|---|---|
| `What is your first and last name?` | `Kirill Petrov` (или название студии) |
| `What is the name of your organizational unit?` | `Mobile` |
| `What is the name of your organization?` | `Self-employed` |
| `What is the name of your City or Locality?` | `Helsinki` |
| `What is the name of your State or Province?` | `Uusimaa` |
| `What is the two-letter country code for this unit?` | `FI` или `RU` |
| `Is CN=..., correct?` | `yes` |

**Проверка:** во второй команде найдите строку `SHA256:` — это отпечаток ключа.
Скопируйте его в блокнот: он должен совпасть с отпечатком в логе CI и в RuStore.

### Вариант A2 (если Java на компьютере нет совсем)

Ключ можно сгенерировать на сервере GitHub — для этого есть отдельный воркфлоу
`docs/ci-keystore.yml`. Порядок:

1. **Сначала** добавьте секрет `KEYSTORE_PASSWORD` — придуманный пароль хранилища
   (Settings → Secrets and variables → Actions → **New repository secret**, имя
   `KEYSTORE_PASSWORD`, значение — пароль). Воркфлоу берёт пароль только из секрета,
   в логах он не появляется.
2. Создайте файл `.github/workflows/keystore.yml` по инструкции из шага C
   (содержимое — `docs/ci-keystore.yml`).
3. Actions → **Создать ключ подписи (один раз)** → **Run workflow** → Run workflow.
4. После успеха: внизу прогона артефакт **signing-key** → скачайте.
   Внутри `app-signing.keystore` и `app-signing.keystore.b64`.
5. Сохраните ключ в двух местах, пароль — в менеджер паролей.
6. **Удалите артефакт и прогон**: в них лежит приватный ключ
   (страница прогона → ⋯ → Delete run; артефакт удаляется вместе с прогоном).
7. Содержимое `app-signing.keystore.b64` вставьте в секрет `KEYSTORE_BASE64` (шаг B).

> Вариант A2 нормален, но ключ проходит через GitHub. Делайте это в **приватном**
> репозитории и не держите артефакт дольше, чем нужно: срок жизни артефакта выставлен
> 1 день специально.

## Шаг B. Четыре секрета репозитория

**Где:** GitHub → репозиторий → **Settings** → **Secrets and variables** → **Actions** →
кнопка **New repository secret**. Повторить четыре раза.

| Name (имя секрета) | Secret (значение) |
|---|---|
| `KEYSTORE_BASE64` | весь файл `app-signing.keystore` в base64 (одна строка) |
| `KEYSTORE_PASSWORD` | пароль хранилища из шага A |
| `KEY_ALIAS` | `sign` |
| `KEY_PASSWORD` | пароль ключа; для PKCS12 — тот же, что пароль хранилища |

**Как получить base64-строку ключа** (вывод — длинная строка, копировать целиком, без пробелов):

Windows, PowerShell (ничего доустанавливать не нужно):

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("app-signing.keystore"))
```

Windows, Git Bash или macOS/Linux:

```bash
base64 -w0 app-signing.keystore          # Git Bash / Linux
base64 -i app-signing.keystore | tr -d '\n'   # macOS
```

Если ключ создан вариантом A2, ничего считать не нужно: содержимое
`app-signing.keystore.b64` — это и есть значение секрета.

**Проверка:** в списке секретов ровно четыре записи. Значения GitHub не показывает
(можно только заменить) — это нормально.

> Самая частая ошибка: добавить секреты не в репозиторий, а в **Environment**.
> Воркфлоу читает секреты репозитория, поэтому такие сборки соберутся без подписи.

## Шаг C. Два файла воркфлоу — создаются руками в веб-интерфейсе

Почему руками: файлы в `.github/workflows/` бот (или токен без права `workflows`)
запушить не может — GitHub отклоняет такую запись. Поэтому это единственные два файла,
которые вы копируете через браузер. Дальше всё собирается само.

### C0. Сначала убедитесь, что код лежит в `main`

Воркфлоу виден в разделе **Actions** только тогда, когда его файл есть в ветке по умолчанию
(**main**), и собирает он ту ветку, которую вы выберете при запуске ребёнка.

- Если код пришёл к вам отдельной веткой (например, `arena/5ecbd877-yandex2`)
  и по ней открыт Pull Request — **влейте его в main** (кнопка **Merge pull request**).
  После этого ветка main = релизный код.
- Если хотите собирать прямо из боковой ветки — создайте файл `.github/workflows/android.yml`
  **дважды**: в `main` (чтобы кнопка запуска вообще появилась) и в этой ветке
  (чтобы GitHub взял содержимое именно оттуда).

### C1. Файл `android.yml` — основная сборка

1. Откройте файл `docs/ci-android.yml` в репозитории:
   `https://github.com/ВАШ_ЛОГИН/yandex2/blob/main/docs/ci-android.yml`
2. Нажмите **Raw** (или значок копирования справа сверху) → выделите всё (**Ctrl+A**) →
   скопируйте (**Ctrl+C**).
3. Вернитесь в корень репозитория (закладка **Code**, ветка **main**).
4. **Add file** → **Create new file**.
5. В поле имени введите ровно: `.github/workflows/android.yml`
   (слэши сами создадут папки).
6. В большом поле вставьте скопированное содержимое.
7. Внизу **Commit changes** → в окне оставьте «Commit directly to the **main** branch» →
   **Commit changes**.
8. Через минуту файл появится по адресу
   `https://github.com/ВАШ_ЛОГИН/yandex2/blob/main/.github/workflows/android.yml`
   — можно открыть и глазами сравнить с `docs/ci-android.yml`.

### C2. Файл `keystore.yml` — только если вы выбрали вариант A2

То же самое, но содержимое берётся из `docs/ci-keystore.yml`, а имя файла —
`.github/workflows/keystore.yml`. После создания ключа (и удаления прогона) этот файл
можно удалить тем же способом, каким создавали: открыть → значок корзины → **Commit changes**.

### C3. Обновление воркфлоу в будущем

Если в репозитории изменился `docs/ci-android.yml` (новая версия), Actions продолжит
работать по **старой** копии в `.github/workflows/android.yml`. Чтобы обновить:
откройте `.github/workflows/android.yml` → значок карандаша (**Edit this file**) →
выделите всё, вставьте новое содержимое → **Commit changes**.

## Шаг D. Запуск и чтение лога

**Где:** GitHub → репозиторий → **Actions** → слева **Android CI** → справа **Run workflow**.

| Поле в форме | Что вводить |
|---|---|
| **Use workflow from** | `main` (или та ветка, где лежит актуальный код) |
| `versionCode для этой сборки` | пусто для первой версии; перед каждой следующей загрузкой в RuStore — `2`, `3`, … |
| `versionName` | пусто или, например, `1.0.1` |

Нажмите зелёную **Run workflow**. Прогон появится в списке (обновите страницу, если
сразу не видно); откройте его — увидите шаги:

| Шаг в логе | Что проверяет/делает | Обычное время |
|---|---|---|
| Код, Java 17, Android SDK | подготовка окружения | 20–60 с |
| Платформа и build-tools | ставит Android 36 и build-tools 36.0.0 | 20–40 с |
| Кэш Gradle | ускоряет повторные сборки | 5 с |
| Проверка настроек рекламы | `ads.testMode=false` и три ID вида `R-M-XXXXXXX-Y` | секунды |
| Статические проверки проекта | `tools/verify_stage1.py`: ресурсы, ссылки, структура | секунды |
| Ключ подписи | восстанавливает `app-signing.keystore` из секрета | секунды |
| Тесты | 95 юнит-тестов чистой логики | 1–2 мин |
| Сборка (debug + release APK + AAB) | `assembleDebug assembleRelease bundleRelease` | 2–6 мин |
| Проверка релизного APK | подпись, наличие боевых ID в APK, разрешения | 10–30 с |
| Итог сборки | сводка: версия, размер, SHA-256, отпечаток ключа | секунды |
| Артефакты | складывает APK/AAB/отчёты | 10–30 с |

**Как понять результат:**

- зелёная галочка у прогона и у всех шагов — всё в порядке;
- жёлтый треугольник — предупреждение, сборка состоялась (например, нет секретов подписи);
- красный крест — сборка не состоялась, ищите `::error` в логе: в сообщении написано,
  что именно исправить.

Внизу страницы прогона есть блок **Summary** (он же открывается сразу после прогона) —
там таблица «что собралось» и что скачать.

## Шаг E. Скачать APK, поставить на телефон, проверить

**Где скачать:** страница прогона → внизу блок **Artifacts**:

| Артефакт | Что внутри | Кому нужен |
|---|---|---|
| **release-apk** | `app-release.apk` (подписанный, для RuStore) и `app-debug.apk` | основной |
| **build-outputs** | всё, что собрал Gradle: APK, AAB, отчёты | если нужен AAB для Google Play |
| **test-report** | HTML-отчёт тестов | если тесты упали |

Артефакт скачивается ZIP-архивом. Распакуйте — внутри `app/build/outputs/...`
(в артефакте `release-apk` файлы лежат плоско: `app-release.apk`, `app-debug.apk`).

**Проверить, что это тот самый файл:** в **Summary** прогона есть строки
«Размер APK», «SHA-256 APK» и «Отпечаток ключа». Сравните отпечаток с тем, что выписали
в шаге A, — они должны совпадать.

### Как поставить APK на телефон без Android Studio

Способ 1 — через `adb` (нужен ещё для логов рекламы). Скачайте **platform-tools**
(≈5 МБ, распаковать в удобную папку): <https://developer.android.com/tools/releases/platform-tools>.
На телефоне: **Настройки → О телефоне → 7 раз тапнуть «Номер сборки»** (включатся
«Для разработчиков») → **Для разработчиков → Отладка по USB**. Подключите кабелем,
подтвердите запрос на телефоне.

```cmd
cd C:\путь\к\platform-tools
adb devices
adb install -r C:\путь\к\app-release.apk
adb logcat -s ConverterAds:V
```

Способ 2 — без кабеля: перекиньте `app-release.apk` на телефон (кабель в режиме передачи
файлов, облако, «Избранное» в Telegram), откройте файл в «Файлах» и разрешите установку
из этого источника. Установщик сам предупредит — это нормально для файла не из магазина.

Способ 3 — отладка на нескольких устройствах: соберите `app-debug.apk` (в том же
артефакте) — он ставится рядом с релизной версией (пакет `com.converterplus.app.debug`)
и не мешает ей.

### Что проверить на телефоне

Коротко (полный список — `docs/STEP_BY_STEP.md`, шаг 5):

- [ ] онбординг → согласие на рекламу → главный экран;
- [ ] изображения JPG ↔ PNG ↔ WEBP;
- [ ] PDF → Изображения (все и выбранные страницы) и Фото → PDF;
- [ ] Извлечение текста: фото документа → TXT с русским текстом;
- [ ] аудио → WAV и M4A; видео → MP4 и «Только звук (M4A)»;
- [ ] свернуть приложение во время конвертации — в шторке идёт прогресс;
- [ ] результат сохраняется в «Загрузки», шторка «Готово!» закрывается;
- [ ] баннер внизу не перекрывает кнопки, межстраничная — после закрытия шторки;
- [ ] «Убрать рекламу на 30 минут» за просмотр видео работает.

В логе рекламы должно быть видно:

| Строка | Смысл |
|---|---|
| `init: пропущено: согласие не получено` | до онбординга — норма |
| `SDK готов: Initialized, testMode=false` | боевые ID, релизный режим |
| `interstitial: загружена` / `rewarded: загружена` | блоки отвечают |

Пока приложение не прошло модерацию РСЯ, креативы будут **тестовыми** — это ожидаемо.

## Шаг F. Следующий релиз

1. Внесли правки в код → закоммитили в `main` (или в ветку, из которой собираете).
2. Actions → **Android CI** → **Run workflow** → в поле
   **`versionCode`** впишите следующий номер (`2`, потом `3`, …) → **Run workflow**.
   Правка `app/build.gradle.kts` не нужна: воркфлоу передаёт номер в сборку как
   `VERSION_CODE`. Хотите всё же зашить номер в код — поменяйте `versionCode = 1`
   на нужный (переменная `appVersionCode` в `app/build.gradle.kts`).
3. Скачайте новый `app-release.apk` из артефакта.
4. RuStore → приложение → **Загрузить версию** → файл → заполнить **Что нового?** →
   отправить на модерацию (`docs/RUSTORE_DEPLOY.md`, раздел 11).

Правила, которые нельзя нарушать при обновлениях: тот же ключ подписи, тот же пакет
`com.converterplus.app`, `versionCode` строго больше предыдущего.

## Что CI проверяет автоматически

| Проверка | Зачем |
|---|---|
| `tools/verify_stage1.py` | все `R.string`/`R.drawable` существуют, импорты и структура не поломаны |
| `testDebugUnitTest` | 95 тестов чистой логики: форматы, правила показа рекламы, имена файлов, история |
| `ads.testMode=false` + три ID вида `R-M-…` | защита от релиза, который показывает демо-рекламу и не приносит денег |
| Подпись релизного APK | без подписи RuStore файл не примет; подпись проверяется `apksigner` |
| Наличие боевых ID **внутри APK** | исключает случай, когда ID правильные в файле, но в сборку попали другие |
| Разрешения APK | хранилище, камера, микрофон запрещены проектом — CI падает, если они появились |
| Версия в APK | в Summary видно `versionCode`/`versionName` фактической сборки |

## Что CI **не** проверяет (делает человек)

- что конвертации реально работают на живом устройстве (список в шаге E);
- как выглядят баннер, межстраничная и rewarded;
- скриншоты, иконку и тексты для магазина;
- модерацию RuStore и связку с кабинетом РСЯ.

## Если прогон упал: разбор частых случаев

| Что видно | Причина | Что делать |
|---|---|---|
| В Actions нет воркфлоу **Android CI** | файл `.github/workflows/android.yml` не в ветке по умолчанию (`main`) | создать файл в `main` (шаг C1) |
| Нет кнопки **Run workflow** | то же самое | то же самое |
| `git push` с `.github/workflows/...` отклонён | у токена/бота нет права `workflows` | создавать и обновлять файл только через веб-интерфейс |
| `::error` про `ads.testMode` или ID блока | в `gradle.properties` тестовый режим или демо-ID | привести к `ads.testMode=false` и `R-M-20230616-2/-4/-7` |
| `::error title=APK не подписан` | неверный пароль, alias или секрет не в репозитории | проверить `KEYSTORE_PASSWORD`, `KEY_ALIAS=sign`, `KEY_PASSWORD`; убедиться, что секреты добавлены в **репозиторий**, а не в Environment |
| `::warning` «Секрет KEYSTORE_BASE64 пуст» | секрет не добавлен | шаг B |
| `Could not find com.yandex.android:mobileads:8.6.0` | репозитории Maven | проверить, что в `settings.gradle.kts` есть `google()`, `mavenCentral()`, `jitpack`; повторить прогон (иногда сбой сети) |
| Упали тесты | в отчёте `test-report` видно какой тест | посмотреть отчёт, править код, запушить снова |
| Ошибки R8/Proguard в release | правила минификации | `app/proguard-rules.pro`: для наших SDK правила уже есть |
| `::error title=ID блока не попал в APK` | сборка подставила другие ID | проверить `gradle.properties`, перезапустить прогон |
| Прогон «завис» больше 45 минут | лимит `timeout-minutes` | перезапустить; при повторе — писать мне с логом |
| `Resource not accessible by integration` | ограничения прав токена при push | не пушить `.github/workflows`, а создавать файл руками |

Лог шага открывается кликом по шагу. Строки `::error` и `::warning` GitHub также
показывает отдельными плашками в шапке страницы прогона.

## Что дальше

1. Скачали `app-release.apk` — публикуйте в RuStore: `docs/RUSTORE_DEPLOY.md`
   (или коротко — `docs/STEP_BY_STEP.md`, шаги 7–11).
2. После публикации добавьте ссылку на карточку RuStore в кабинет РСЯ
   (`docs/STEP_BY_STEP.md`, шаг 12) — до этого доход не начисляется.
3. Следите за отпечатком ключа: он должен совпадать в логе CI, в окне `apksigner`
   и в консоли RuStore. Если он вдруг изменился — значит, в секреты попал другой ключ,
   и обновления «поверх» у пользователей не установятся.

Дополнительно:

- `docs/ci-android.yml` — содержимое основной сборки (копируется в `.github/workflows/android.yml`);
- `docs/ci-keystore.yml` — одноразовая генерация ключа (копируется в `.github/workflows/keystore.yml`);
- `docs/APK_RELEASE.md` — тот же релиз, но локально;
- `docs/STEP_BY_STEP.md` — полный рунбук от установки Android Studio до статуса «Активно».
